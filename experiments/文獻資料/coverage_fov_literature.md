# 網格大小 vs 相機視角(FOV)覆蓋率 — 文獻回顧

目的：驗證「網格切太大導致漏球」這個假設，用文獻裡覆蓋路徑規劃(Coverage Path Planning, CPP)
的公式，算出以我們車體的相機參數 (水平視角 80°、有效偵測距離 3m)，理論上網格最大可以切多大
才能保證100%覆蓋，而不用自己真的跑模擬試錯。

## 車體參數 (取自 [simple_bot.urdf](../../src/tennis_bot/urdf/simple_bot.urdf) 跟
[vision_node.py](../../src/tennis_bot/tennis_bot/vision_node.py) 註解)
- 水平視角 `horizontal_fov = 1.396 rad ≈ 80°`（半角 θ = 40°）
- 有效偵測距離 `R ≈ 3m`（門檻調整後量測值）
- 目前網格：8欄×4排，每格 2.75m(x) × 2.25m(y)

## 找到的3篇最相關文獻

1. **Bähnemann, R., Lawrance, N., Chung, J.J., Pantic, M., Siegwart, R., Nieto, J. (2019).
   "Revisiting Boustrophedon Coverage Path Planning as a Generalized Traveling Salesman Problem."**
   ETH Zurich, Autonomous Systems Lab.
   PDF: https://jenjenchung.github.io/anthropomorphic/Papers/Baehnemann2019revisiting.pdf

   關鍵結論：弓字型 (boustrophedon) 覆蓋路徑中，相鄰兩條掃描線的間距，**必須等於感測器
   footprint 的寬度**，才能保證掃過去時不留縫隙（原文：*"The sensor footprint hereby
   defines the offset distance."*）。這篇是空拍機用向下相機（footprint是矩形長條），跟我們
   車體「相機朝前」的幾何不同，但「間距 = footprint 寬度」這個核心原則是通用的。

2. **Nospes, D., Stütz, P. (2024). "Sensor and Coverage Path Planning for the Monitoring of
   Aircraft Emergency Landing Sites."** ICAS 2024 (34th Congress of the International Council
   of the Aeronautical Sciences).
   PDF: https://www.icas.org/icas_archive/icas2024/data/papers/icas2024_0706_paper.pdf

   關鍵結論：用感測器錐形視野 (sensor cone) 的寬度當作掃描線間距，並且**額外乘上一個
   0.8 的安全係數**，因為實際上雲台/感測器角度控制一定會有誤差，不能照理論值算好算滿
   （原文：*"we include an additional safety factor sf of 0.8 into the calculation of the
   distance between sensor sweeps... increases the coverage in non-perfect conditions."*）。
   這點對我們很重要——我們的視覺是即時偵測，不是完美幾何，理論值也該打折。

3. **Chowdhury Choton, J., Kim, ... et al. "Fast-Revisit Coverage Path Planning for Autonomous
   Mobile Patrol Robots Using Long-Range Sensor Information."** arXiv:2501.07343 (2025)。
   PDF: https://arxiv.org/pdf/2501.07343

   關鍵結論：這篇是**地面巡邏機器人**+扇形FOV感測器（跟我們幾乎一樣的設定，FOV測試
   90°/120°，偵測半徑5m），但他們的做法是**不用大格子**，而是用很細的佔用網格
   (0.05m/cell)，每一幀持續判斷「這個小格子現在在不在扇形視野內」來標記已掃過，
   而不是像我們現在「只在格子中心判斷一次」。這篇間接說明：業界對付扇形FOV漏偵測的
   標準做法，是縮小判斷粒度、連續判斷，而不是單純放大/縮小巡邏格子。

## 套用到我們的車體：算出來的網格上限

我們車體相機朝「前方」（不是像上面兩篇那樣朝下），所以正確的幾何不是「矩形長條」，
而是「扇形視野沿著直線移動時，能掃到的最大側向距離」。

推導（跟上面3篇的「間距=footprint寬度」原則一致，只是footprint形狀換成扇形）：
車體沿一條直線（一整排）持續前進、朝向固定不變，某個球在垂直於行進方向、離路徑
`d` 公尺的地方。球「有沒有機會被看到」的條件是：存在某個車體位置，同時滿足
(1) 距離 ≤ R，(2) 夾角 ≤ θ(半視角)。可以證明這個條件成立的臨界值是：

```
d_max = R × sin(θ)
```

代入 R=3m, θ=40°：

```
d_max = 3 × sin(40°) ≈ 3 × 0.643 ≈ 1.93m
```

也就是一整排的「有效可視寬度」= `2 × d_max ≈ 3.86m`，這才是理論上排間距(row spacing,
也就是 `cell_h`) 的上限。乘上文獻②建議的 0.8 安全係數：

```
安全排間距 ≈ 3.86 × 0.8 ≈ 3.09m
```

## 結論（跟原本猜測不太一樣）

**目前的 `cell_h = 2.25m`，已經比理論安全上限 3.09m 小很多** —— 照這個公式來看，
排間距（南北方向）**不是**漏球的主因，就算不縮小網格，Y方向理論上也該有覆蓋餘裕。

而 `cell_w`（東西方向，欄間距 2.75m）在這個「相機朝前、沿整排直線走」的模型下，
其實**跟覆蓋率無關**——只要車體在整排移動時朝向都固定沿著這排走，扇形視野會連續掃過
整條 22m 長的路徑，格子怎麼切欄跟看不看得到球無關，只影響車體多常抵達一個「waypoint」。

所以文獻③的發現比較可能是我們漏球的真正原因：問題不是格子太大，而是——
1. **排跟排轉彎的角落**：車體在排尾轉向下一排時，朝向不再沿著直線，那段時間扇形視野
   沒有掃過去，形成真正的死角，跟格子大小無關。
2. **偵測到球之後偏離直線去追**：一旦 ALIGN/APPROACH 觸發，車體轉向去追那顆球，
   原本那一整排「應該要掃到底」的直線路徑被打斷，後段路徑可能沒掃完就切到下一排了。
3. **3m有效距離不是每個角度都一樣準**：threshold 是用畫面中球的面積(px²)算出來的，
   球在畫面邊緣(接近40°那條邊)時因為透視關係，量到的面積可能比中心小，實際上有效
   偵測距離在扇形邊緣可能比中心的3m短，也就是理論值的80°可能沒有全部有效。

**建議**：與其縮小網格（會拉長總耗時、跟你要的「低投入」方向衝突），可以先驗證第1、2點
——比如在資料裡看漏掉的球是不是集中在「排尾轉彎附近」或「車體剛追完一顆球回到PATROL」
這種情況，如果是，那切更細網格其實沒有解決根本問題。

## 後續驗證（用 run2 實際資料檢查，2026-08-15 補充）

檢查 run2 沒撿到的 4 顆球（ball_1, ball_2, ball_7, ball_9）在整趟軌跡中「離球最近的那個
瞬間」車體是什麼狀態、離球多遠：

| 球 | 最近距離 | 當下狀態 | 側向偏移(離該排中心線) |
|---|---|---|---|
| ball_1 | 0.24m | **PATROL**（直線前進中） | 0.23m |
| ball_2 | 0.51m | **PATROL** | 約0.5m |
| ball_7 | 0.44m | **PATROL** | 約0.4m |
| ball_9 | 0.67m | **PATROL** | 約0.7m |

**這推翻了「主因是排尾轉彎死角」的猜測**——這4顆球全部是在車體直線巡邏(PATROL)、離路徑
不到0.7m的時候錯過的，遠小於前面算出的理論可視寬度 d_max=1.93m。也就是說：即使幾何上
（距離、角度）都在相機理論範圍內，實際上還是沒有觸發偵測。

這代表問題不是網格大小、也主要不是轉彎死角，而是**視覺偵測本身在理論FOV範圍內就不可靠**，
可能原因：
- 球在畫面邊緣（接近40°那側）時，YOLO/輪廓偵測的準確度或觸發的像素面積門檻，實際上沒有
  真的撐到 3m——理論上的80° FOV，實際有效偵測角度可能窄很多。
- `/target_position` 的更新/判斷邏輯本身可能有沒發現的問題（例如某一幀漏判、或者只在
  特定條件下才發佈）。

下一步如果要真的解決漏球問題，應該去量測「不同角度、不同距離下，球實際多容易被偵測到」
（例如固定球在畫面不同偏移角度，看 vision_node 多少距離內還抓得到），而不是繼續調整網格
大小。

## 實測驗證（2026-08-15，run4 + vision_node 逐幀log）

在 `vision_node.py` 加了逐幀 debug log（每幀的輪廓數量、最大面積、有沒有判定成球），
重新正確跑了一次(run4，車體有先傳送到格1)，比對6顆沒撿到的球在幾何可視窗口內
(距離≤3m 且 夾角≤40°) 實際的視覺偵測狀況。結果：

**6顆漏掉的球，在各自的幾何可視窗口內，輪廓面積幾乎全程是 0px²**——不是「面積太小、
差一點點過門檻」，是幾乎完全沒偵測到任何黃色色塊，即使車體當時離球只有 0.14~1.08m
（例如 ball_3 最近距離只有 0.14m，ball_1 只有 0.37m，都遠比理論上該偵測到的距離近很多）。

對照組：**4顆真的撿到的球**（ball_6/8/4/5），在 `vision_debug.csv` 裡的模式完全不同——
一開始被偵測到時，輪廓面積就已經有 263~441px²（換算實際距離大約只有 1.3~1.5m，
遠比程式註解寫的「3m有效距離」近很多），然後隨距離拉近平滑放大到幾千px²，是連續、
乾淨的偵測曲線。

**結論修正**：
1. **程式註解裡「有效偵測距離約3m」是理論值，實測明顯沒有這麼遠**——真正開始穩定偵測
   到球，大概要到 1.3~1.5m 內。前面用 3m 算出來的 `d_max=1.93m`、安全排間距 3.09m，
   這些數字本身要打對折重算，用 1.5m 代入：`d_max = 1.5×sin(40°) ≈ 0.96m`，
   安全排間距只剩 `2×0.96×0.8 ≈ 1.55m`——已經比現在的 `cell_h=2.25m` 還小，
   這樣才終於能跟「排間距內漏球」的實測結果對上。
2. **更關鍵的是：漏掉的球全部是車體在 PATROL 直線巡邏、球在視野側邊經過時發生的；
   撿到的球全部是 ALIGN/APPROACH 狀態、車頭正對著球衝過去時發生的。** 即使漏掉的球
   距離車體只有 0.14~0.37m（遠比任何撿到案例的「首次偵測距離」1.3~1.5m 近很多），
   還是整段時間 0 偵測——這代表問題不是「距離不夠近」，而是**球在畫面側邊/邊緣時，
   偵測幾乎完全失效**，不是漸弱、是幾乎斷崖式的有/無之分。可能原因：相機沒有向下俯角
   （已知的近距離死角問題），球在側邊+近距離時的合成角度剛好落到垂直視野外；或者
   相機鏡頭是往車體側邊偏移安裝(y方向偏移0.1m)，車體自己的前車體外殼在大角度時
   把視線擋住了一部分。

**這代表原本套文獻公式算出來的「網格安全上限」全部要打折**，而且**光縮小網格沒辦法
解決側邊漏偵測的問題**——因為就算格子切超小、車體離球剩不到0.4m，只要球是從側邊經過
而不是正對著衝過去，一樣偵測不到。真正的槓桿點是相機視野本身（例如加一點向下俯角、
或重新校準顏色/面積門檻），而不是網格大小。
